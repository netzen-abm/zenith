# Core Reconciliation Matrix

**Status:** Working architectural reconciliation artifact  
**Basis:** Verified live Supabase Core/Audit contract and repository migration inventory  
**Scope:** Core/Audit only; Supabase-managed infrastructure is explicitly out of scope

## Purpose

This matrix converts the verified live contract into bounded repository reconciliation units. It is intentionally object-oriented: an object is considered reconciled only when its definition, constraints, indexes where material, RLS, grants, function security context, triggers, views, and sensitive-data behavior are represented or explicitly classified.

The live project currently contains 14 applied migration generations. The repository contains only `0001_security_kernel.sql` and `0002_capability_policy_boundary.sql`. Therefore the repository is not yet a complete reproduction of the live contract.

## Foundation object map

### `core.organisations`

- Live canonical table.
- UUID primary identity with generated UUID default.
- Required `name` and `slug`; timestamps generated by default.
- RLS enabled.
- Authenticated read policy is membership-derived through resources and resource memberships.
- Must not be replaced with a weaker organisation-wide authenticated read rule.

### `core.identities`

- Live canonical table includes `id`, `auth_user_id`, `display_name`, `created_at`.
- `auth_user_id` is the bridge to Supabase Auth.
- Current identity resolution uses the verified live Auth context through `auth.uid()`.
- RLS is enabled and the self-read policy is `id = core.current_identity_id()`.
- Historical transaction-local `app.identity_id` semantics must not be reintroduced.

### `core.resources`

- Canonical protected resource boundary.
- Required organisation, type, title and epistemic status.
- `sensitivity` defaults to `public`.
- Optional PostGIS `geom`.
- RLS enabled.
- Anonymous read is restricted to `sensitivity = 'public'`.
- Authenticated read is public OR delegated through `core.can_read_resource(id)`.
- This table is the primary dependency for capability authorization and public projections.

### `core.resource_memberships`

- Resource-to-identity membership relation.
- Required `resource_id`, `identity_id`, `membership_role`.
- RLS enabled.
- Authenticated read is self-scoped or delegated through resource readability.
- Membership semantics must remain compatible with `can_read_resource` / `can_write_resource`.

### `core.policy_obligations`

- Resource-scoped policy obligations represented as JSONB.
- RLS enabled.
- Authenticated reads delegate to `core.can_read_resource(resource_id)`.
- This is a policy-data layer, not a replacement for the authorization decision boundary.

## Security contract

All live Core/Audit base tables have RLS enabled. The verified live policies are predominantly authenticated-only and delegate protected access to the canonical resource authorization helpers. The only direct anonymous base-table read currently verified is the public resource policy on `core.resources`; public-facing projections are separately controlled.

The canonical capability function remains fail-closed for unknown actions and uses the live Auth-derived identity/organisation context. SECURITY DEFINER helpers use the hardened execution context with an empty `search_path`; direct execution of the protected authorization helpers remains closed to public callers.

No reconciliation migration may:

- disable RLS;
- broaden anonymous access to protected tables;
- replace resource-level authorization with organisation-only access;
- expose precise sensitive coordinates through public projections;
- restore obsolete transaction-local identity context;
- grant direct public execution of protected SECURITY DEFINER helpers;
- treat an unknown capability as allowed.

## Public projection contract

The live Core contract includes six public projections:

- `core.public_resources`
- `core.public_entity_relationships`
- `core.public_resource_spatial_relations`
- `core.public_resource_time_spans`
- `core.public_spatial_representations`
- `core.public_research_questions`

They are part of the public API surface and must be reconciled from their exact verified definitions, not recreated merely because names match.

`public_resources` filters to public resources and exposes geometry only under public sensitivity. `public_spatial_representations` exposes geometry only for public resources and permitted precision levels (`generalized`, `regional`, `unknown`); coordinate precision/confidence must not become a leakage path for sensitive locations.

## Platform-managed classification

PostGIS is installed in the public schema and is platform-managed. Reconciliation must preserve the required extension dependency without blindly reconstructing Supabase-managed extension objects. The known advisor residual around public PostGIS objects remains a documented platform concern unless a concrete security defect is demonstrated.

## Verification order

1. Reproduce the foundation on a disposable fresh database.
2. Verify exact columns, defaults, constraints and indexes.
3. Verify RLS is enabled on every protected base table.
4. Verify policies and role grants exactly.
5. Verify SECURITY DEFINER ownership, `search_path`, and EXECUTE ACLs.
6. Verify public projection definitions and anonymous exposure.
7. Verify sensitive-coordinate behavior.
8. Add real Auth identities for authenticated positive/negative tests; until then, authenticated runtime tests remain explicitly unexecuted.
9. Only after fresh-database verification, prepare a production forward migration.

## Current implementation boundary

The next migration should cover **Foundation only**. Evidence, knowledge graph, space/time, research and public projections remain separate bounded units. This avoids a monolithic reconciliation migration and makes failures attributable to one architectural layer.

## Non-goals

- Do not reconstruct `auth`, `storage`, or other Supabase-managed schemas.
- Do not silently mutate existing production data.
- Do not delete historical repository migrations.
- Do not move PostGIS merely to satisfy an advisor warning.
- Do not claim database parity from green GitHub CI alone.
- Do not claim authenticated authorization tests passed while the Auth test population is empty.
