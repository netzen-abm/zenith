# Authorization / Operation Convergence Audit — 2026-09-18\n\n## Scope\n\nAudit the repository after ADRs 0001–0009 and the executable operation contracts. The audit searches for authorization-boundary, identity-context, capability, lease, and operation references and compares them with the canonical contracts.\n\n## Current canonical path\n\nAuth User → ZENITH Identity → Organisation Membership → Active Organisation Context → Authorization / Policy → Capability / Lease → Operation → Execution Reauthorization → Audit / Provenance → Release.\n\n## Findings\n\n### 1. Canonical authorization boundary\n\n`core.authorize_capability(action, resource_id, purpose)` remains the database authorization entry point. It delegates resource decisions to `can_read_resource` / `can_write_resource`. Unknown actions fail closed.\n\n**Status: CONVERGED.**\n\n### 2. Identity / organisation context\n\nThe repository contains the explicit identity-to-organisation context migration and its fresh-DB assertions. No replacement operation-level organisation inference was found.\n\n**Status: CONVERGED.**\n\n### 3. Capability and operation contracts\n\n`packages/contracts/src/operation.ts`, `operation-state.ts`, and `operation-policy.ts` define operation identity, lifecycle, idempotency scope, retry classification, expiry, and terminal-state behavior.\n\n**Status: CONVERGED at contract level.**\n\n### 4. Execution lease\n\n`packages/contracts/src/execution.ts` validates lease identity, operation identity, capability, purpose, revocation, and expiry.\n\n**Status: CONVERGED at contract level.**\n\n### 5. Important remaining boundary\n\nLease validation is not itself the current authorization decision. The runtime must perform both checks:\n\n1. validate the operation's lease;\n2. reauthorize the action against current policy at execution/synchronization time.\n\nThe current repository has the contracts for these boundaries but does not yet contain a production execution service wiring them together.\n\n**Status: OPEN — highest-value runtime gap.**\n\n### 6. Duplicate authorization implementations\n\nThe repository search found the canonical SQL authorization functions and their tests, plus the TypeScript authorization contract. No second production authorization engine was found in the current scaffold.\n\n**Status: NO DUPLICATE PRODUCTION AUTHORITY FOUND.**\n\n### 7. Direct protected-data paths\n\nThe current application directories are still scaffold-level and do not expose a separate application data-access authorization path. Database RLS remains the protected-data enforcement layer.\n\n**Status: CONVERGED for current repository maturity.**\n\n### 8. Offline synchronization\n\nThe resilient contract requires receiving-side authorization recheck and prohibits stale leases from authorizing execution. The execution/reconciliation contract now expresses these requirements.\n\n**Status: CONTRACT CONVERGED; RUNTIME NOT YET IMPLEMENTED.**\n\n## Architectural conclusion\n\nDo not add another authorization helper, policy engine, or per-adapter permission system.\n\nThe next runtime boundary should be a single execution coordinator that composes:\n\n`authorize_capability → lease validation → operation state validation → idempotency decision → execution → audit/reconciliation → release`.\n\nAdapters must call this coordinator rather than implement authorization independently.\n\n## Deferred work\n\n- persistent operation store\n- queue/scheduler adapter\n- transport adapters\n- distributed locking\n- provider adapters\n- domain-specific conflict resolution\n- production execution service\n\nThese remain deferred until the convergence boundary is executable and tested end-to-end.\n\n## Verification note\n\nThis is a repository/static convergence audit. It does not claim authenticated production-runtime tests because the repository currently has contract/scaffold-level application code and the earlier Core environment has no seeded authenticated users.
